Part 1 · The build

The shape of the project

Three ideas carry the whole thing. Everything else is detail.

1 · The root scene never unloads

main.tscn is the running scene from launch to quit. Menus show and hide inside it; the map is added inside it. Nothing ever calls change_scene_to_file(). That matters because Godot's multiplayer replicates by node path — if the host says "spawn a player at World/Players", that path has to exist on every client at that exact moment. A root scene that never goes away is the simplest way to guarantee it.

2 · Only players are networked

The map is generated identically on every machine from a fixed seed, so not one byte of level geometry crosses the wire. The only replicated objects are the player bodies. This is why the game feels instant on a LAN.

3 · Characters are data, not code

A playable character is a .tres resource file, discovered by scanning a folder. Adding your fourth character never touches a script.

The one rule to remember

Every peer runs the same code and builds the same world. The network only carries who is playing, as what, and where they are. When you extend this project, keep asking: can this be derived locally instead of sent?

STEP 01

The scene tree

Here is main.tscn in full. It is small on purpose.

Main (Node)runs main.gd — screen flow + spawning
├── World (Node3D)everything that exists in 3D
│ ├── MapRoot (Node3D)the map scene gets added here
│ ├── Players (Node3D)spawned player bodies land here
│ └── PlayerSpawner (MultiplayerSpawner)spawn_path = ../Players
└── UI (CanvasLayer)draws on top of the 3D view
    ├── MainMenuinstance of main_menu.tscn
    ├── CharacterSelectinstance of character_select.tscn
    └── HUDinstance of hud.tscn

Why these particular nodes

MapRoot and Players are separate so that leaving a world can free the map and the players independently, and so that a future map switch never disturbs the spawn path.

PlayerSpawner is a MultiplayerSpawner. Its single configured property is spawn_path, pointing at ../Players. When the server calls spawner.spawn(data), Godot creates the node locally and tells every connected client to create it too. Late joiners get every already-spawned player automatically — you do not have to write catch-up code.

UI is a CanvasLayer, not a plain Control. A CanvasLayer draws independently of the 3D camera, so the HUD stays put no matter where the player looks.

Building it yourself

If you were recreating this from an empty project: new scene → root type Node, named Main. Add Node3D named World. Inside it add two more Node3Ds named MapRoot and Players, then add a MultiplayerSpawner named PlayerSpawner. Select it and, in the inspector, set Spawn Path to ../Players. Add a CanvasLayer named UI as a sibling of World, and drag your three UI scenes into it. Save as res://scenes/main.tscn and set it as the main scene in Project → Project Settings → Application → Run.

Easy mistake

The MultiplayerSpawner's Auto Spawn List (the inspector array of scenes) is for the simple case where the spawner instantiates a scene with no arguments. We do not use it — we set spawn_function in code instead, because each player needs a name, a character, an authority and a position. Leave the auto-spawn list empty.

STEP 02

Autoloads: GameState and NetworkManager

Two singletons, registered in Project Settings → Globals → Autoload. Order matters: GameState must be above NetworkManager, because NetworkManager reads the player's chosen character out of GameState when hosting.

GameState — the character roster

Its whole job is: know every available character, and remember what the local player picked. The interesting part is that it finds characters by scanning a directory rather than by a hardcoded list.

Two details worth copying into your own projects. files.sort() makes the order deterministic — that is why the resources are named 01_knight, 02_mage, 03_rogue, so you control the order on the select screen by renaming files. And the .remap handling matters once you export the game: Godot renames resources during export, and a directory scan that ignores this works in the editor and silently finds nothing in the shipped build.

NetworkManager — the peer and the roster

It owns the ENet peer and a dictionary of who is connected. It deliberately knows nothing about the 3D world; it emits signals and lets main.gd decide what to do.

The host is always peer 1 in Godot. Notice that the host registers itself into the roster by hand and immediately emits player_registered(1) — the host never goes through the network handshake, so without this line the host would never spawn a body for itself.

The handshake RPCs

Read the @rpc annotations carefully, because they are the security model:

  • @rpc("any_peer") means any client may call this on the server. Anything marked this way is an attack surface — hence the explicit is_server() guard, the length clamp on the name, and validating the character id against the known list instead of storing whatever was sent.
  • @rpc("authority") means only the server may call it. The roster broadcast is one-directional by design.
  • "reliable" means ENet retries until it arrives. Use it for events that must not be dropped. Continuous state like position uses unreliable delivery instead, which the MultiplayerSynchronizer handles for you.
STEP 03

CharacterData — characters as data

A custom Resource subclass. Because it declares class_name, Godot registers it engine-wide and it appears in the Create Resource dialog and the inspector like a built-in type.

@export_group is cosmetic but earns its keep — it turns a flat wall of twenty fields into four collapsible sections in the inspector.

The field that travels over the network is id. Everything else is looked up locally from that id, which is why the string is worth being careful with:

Don't change an id later

id is the only part of a character that crosses the wire. Renaming "knight" to "paladin" after players have saved characters means those saves point at nothing. Rename display_name freely; treat id as permanent.

Switching first and third person

Both modes use the same rig. Third person extends the spring arm and offsets it over the shoulder; first person collapses the arm to zero and nudges the camera forward past the model's face.

What the synchronizer replicates

Select the MultiplayerSynchronizer node and the replication panel opens at the bottom of the editor. Three properties are configured:

Authority is what decides who may write these. It is assigned at spawn, in main.gd, and — critically — before the node enters the tree, so the synchronizer sees the right owner from its very first frame.

STEP 05

The three UI screens

Each screen is its own scene, instanced into UI. None of them know about each other or about networking — they raise signals, and main.gd wires them together. That is what keeps them re-orderable.

Main menu

Structure is a full-rect ColorRect background, a CenterContainer, and a VBoxContainer column holding the title, a two-column GridContainer of labelled fields, and the buttons.

The %NodeName syntax is Godot 4's scene-unique names. Tick Access as Unique Name on a node in the scene dock and you can reach it with %Name from anywhere in that scene, no matter how deeply you later re-nest it. In a UI built from containers — where you will re-nest things — this saves constant path breakage.

Character select

This is the most interesting screen, because the cards are built in code and each one contains a live 3D viewport.

own_world_3d = true is the key property. Without it, every preview viewport would render the game world. With it, each card gets a private little 3D scene — which is also why each one needs its own light and environment, since it cannot borrow the game's.

The pivot node is stored as metadata so _process can spin it, faster for the selected card:

And refresh() rescans the character folder every time the screen opens, which is why a newly added .tres shows up without restarting the game.

HUD

The root Control has mouse_filter = Ignore so clicks pass through to the game — but note that this only affects the root itself, so the pause menu's buttons inside it still work normally.

The HUD finds the local player through a group rather than a node path, which keeps it decoupled from where players are spawned:

Escape opens the pause panel and releases the mouse; clicking on the world re-captures it. That pair of behaviours lives in hud.gd's _unhandled_input, and the player script ignores all input whenever the mouse is not captured — which is what stops your character from running around while you are clicking menu buttons.

STEP 06

main.gd, the conductor

Every connection in the project is made in one _ready(). If you want to know how the game is wired, this is the only place you have to read.

The spawn function

This is the heart of the multiplayer. It runs on every peer — the server runs it when it calls spawn(), and each client runs it when the replicated data arrives.

Four rules are packed into those eight lines:

  • Set every property before returning. The spawner adds the node to the tree after your function returns, so anything set here is guaranteed to be in place before _ready() runs. That is how character_id is available in time for the model to be built.
  • Name the node deterministically. P7 on the host must be P7 on every client, because the synchronizer matches nodes by path. The P prefix avoids a node name that is purely numeric.
  • Set authority before the node enters the tree, for the same reason.
  • Only send plain data. The dictionary is serialised across the network, so it holds ints, strings and a Vector3 — never a node reference or a loaded resource.

The server side is correspondingly small:

Note _map.has_method("get_spawn_point"). That duck-typed check is the entire contract between the game and a map — any scene that implements that one method can be a map.

Entering and leaving

Leaving tears down players and map but leaves Main, World and the spawner untouched — so you can host, leave, and join somewhere else without a single scene reload.

STEP 07

The network handshake

The ordering here is the part people get wrong. A client must not announce itself until it can receive spawns, or player bodies arrive before there is anywhere to put them.

Host · peer 1
Joining client
  1. 01host_game() opens the ENet server on port 7777.
    —
  2. 02Adds itself to the roster as peer 1, emits player_registered(1), loads the map, spawns its own body.
    —
  3. —
    03join_game() creates an ENet client and connects.
  4. waiting
    04connected_to_server fires. The client loads the map first, then calls send_registration().
  5. 05_register arrives. Validates the name and character id, stores them in the roster.
    —
  6. 06Broadcasts the full roster with _sync_roster.rpc() so every HUD updates.
    —
  7. 07Emits player_registered(peer); main.gd calls spawner.spawn().
    —
  8. —
    08Receives the spawn, plus one for every player already in the world. Runs _spawn_player for each.
  9. 09On disconnect: peer_disconnected → roster erased, re-broadcast, body freed.
    —

Part 2 · Working with it

Importing your own character model

Right now all three characters render as coloured capsules, because model_scene is empty and player.gd falls back to a built-in placeholder. Here is the full swap.

1 · Get the file into the project

Create res://models/ and copy your .glb or .gltf in — either through the OS file manager (Godot imports on next focus) or by dragging into the FileSystem dock. glTF is strongly preferred over FBX; FBX needs an external converter and imports less predictably.

2 · Check the import settings

Double-click the imported file to open the Advanced Import Settings dialog. What matters here: your animations appear in the list on the left, and each one has a name. Write those names down exactly — you need them in step 4. If your model came as one long take, this dialog is also where you slice it into clips.

3 · Point a character at it

In res://resources/characters/, click 01_knight.tres. In the inspector, drag your imported scene into Model → Model Scene. Save with Ctrl+S.

4 · Fill in the animation names

Under Animation Names, type the clip names exactly as they appear in your model's AnimationPlayer — commonly things like Idle, Walking, Running. Leave a field blank to skip that state. The lookup is defensive, so a wrong name is silently ignored rather than crashing:

You do not have to find the AnimationPlayer yourself — player.gd searches the imported model recursively for the first one it contains.

5 · Fix the scale and the footing

The collision capsule is 1.8 m tall with a 0.4 m radius, and its bottom sits at local y = 0. Your model's feet must land there too.

SymptomField to adjust
Model is tiny or giganticmodel_scale — Blender exports at 1 unit = 1 m, so usually 1.0. A model authored in centimetres needs 0.01.
Floating above the groundmodel_offset — lower Y, e.g. Vector3(0, -0.1, 0).
Sunk into the floormodel_offset — raise Y.
Camera inside the head in first personhead_height — set to your model's actual eye level in metres.
Facing the wrong waymodel_yaw_offset_deg — see the next section.

6 · Add a fourth character

Right-click in res://resources/characters/ → New Resource → search CharacterData. Save it as 04_yourname.tres. Give it a unique id and fill in the fields. It will appear on the select screen the next time that screen opens — no code, no restart.

Naming controls order

Cards are ordered by filename, because game_state.gd sorts the directory listing. Rename the files to reorder the select screen.

Making sure the model faces the right way

There are two separate facing problems, and they look identical on screen. Diagnosing which one you have saves a lot of time.

Problem A — the code's rotation math

This is the bug that was in the project until it got fixed, and it is worth understanding because it explains the confusing symptom of both forward/back and left/right seeming reversed at once.

In Godot, a node's forward axis is -Z. Rotate a node by yaw t around Y and its forward vector becomes (-sin t, 0, -cos t). So to make it face a direction (x, 0, z) you need t = atan2(-x, -z). Using atan2(x, z) instead gives you a yaw exactly 180° off:

Because the error is a half-turn, it flips every axis at once. That is the tell: if forward, back, left and right all look mirrored, you have one rotation bug — not four input bugs. Do not "fix" it by reversing your input actions or negating the WASD axes. Movement was never wrong; only the model's rotation was. Reversing input breaks the thing that worked and leaves the real bug in place.

You can check the math without running the game. Save this as facing_check.gd in the project root and run Godot.exe --headless --path . --script res://facing_check.gd:

Use the local basis, not the global one

A first attempt at that script used node.global_transform.basis and printed nonsense, because a node added during _init is not in the tree yet and global_transform silently returns identity. Building a Basis directly, as above, needs no tree at all.

Problem B — the model itself faces +Z

The code is now correct, so if your imported model still looks backwards, the model was authored facing the other way. Many artists model characters looking down +Z; Godot expects -Z.

Fix it in the resource, not the code: set model_yaw_offset_deg = 180 on that character's .tres. This is per-character on purpose, because it varies per model — one asset pack may face +Z and the next -Z, and a code-level fix would break every model that was already correct.

Telling the two apart in ten seconds

  1. Press V to go first person, then back to third person. In first person the body locks to the camera through a separate code path, so the two problems behave differently.
  2. Walk forward in third person and watch the placeholder capsule on another character — it has a small nose pointing along -Z. If the capsule faces correctly but your imported model does not, it is Problem B, and model_yaw_offset_deg = 180 fixes it.
  3. If even the placeholder capsule faces backwards, it is Problem A — check the atan2 line in _simulate_local.

Testing multiplayer locally

You need two running instances. There are three ways, in increasing order of usefulness.

Option 1 — Godot's built-in multi-run

Debug → Customize Run Instances…, tick Enable Multiple Instances, set the count to 2, and press F5. Godot launches both windows. Simple, but both start at the main menu and you click through by hand each time.

Option 2 — the quick-connect flags

This is why _apply_command_line() exists. Everything after -- is passed to the game, and the two windows go straight into the world with a character already chosen:

FlagEffect
--hostHost immediately on the default port.
--join <address>Connect to that address.
--port <n>Override port 7777.
--name <text>Skip typing a name.
--character <id>Skip the select screen. Omit it to stop there instead.

Option 3 — a headless dedicated server

Add --headless to the host command and it runs with no window and no renderer, printing to the terminal. This is how the project was verified: run a headless host, connect a headless client, and read the log.

Those three lines confirm the whole chain: the server opened, the handshake completed with the client's chosen character intact, a distinct spawn point was assigned, and disconnect cleanup ran. If you ever need to prove replication reached the client, drop a temporary print() into Player._ready() showing name, is_multiplayer_authority() and character_id; on a healthy two-player session each side prints both players, with authority true for exactly one.

Playing with someone else

  • Same network: the host runs ipconfig and shares their IPv4 address; the other player types it into the Server Address field.
  • Over the internet: forward UDP port 7777 to the host machine, and let the game through Windows Firewall when prompted. If you would rather not touch the router, a tool like Tailscale or ZeroTier puts you both on one virtual LAN and the LAN instructions then apply unchanged.

Designing your own maps

Is the world random?

No — and this is worth being precise about. arena.gd builds the level in code, but from a fixed seed:

Same seed, same code, same layout — every launch, on every machine. That is deliberate: because all peers derive the identical world locally, no geometry is ever sent over the network. Change BLOCK_SEED and you get a different arena, but every player must be running the same build, or they will be walking through different worlds while agreeing on their coordinates.

The arena is scaffolding. It exists so there was something to walk around in on day one. You are meant to replace it.

Hand-building a map in the editor

The only contract a map has to satisfy is one method. Anything else is up to you.

  1. New scene, root type Node3D. Save as res://scenes/maps/forest.tscn.
  2. Add a WorldEnvironment and a DirectionalLight3D — without them your map renders black. The quickest route is to copy those two nodes out of arena.tscn.
  3. Build the geometry. Three approaches, pick per map:
    • CSG blockout — add CSGBox3D / CSGCylinder3D nodes, tick Use Collision on each. Fastest for prototyping; not the most efficient at runtime, so treat it as temporary.
    • Imported mesh — model in Blender, export glTF. Suffix any mesh name with -col and Godot generates a collision body for it on import. This is the production path.
    • GridMap — build a MeshLibrary of tiles and paint them. Ideal for dungeons and anything modular.
  4. Add a Node3D named SpawnPoints and put several Marker3D children inside it, positioned where players should appear (roughly 1 m above the floor).

Collision layers

Put all static level geometry on layer 1. Players are on layer 2 and only collide with layer 1, and the third-person spring arm also only tests against layer 1 — so geometry left on the wrong layer will let the camera pass straight through walls.

Adding map selection

Yes, this works, and the project is already shaped for it. It is not built yet — here is the recipe, which deliberately mirrors how characters already work.

The one new problem is that a map is a session-wide choice, not a per-player one. The host picks; every client must load the same one. So the map id has to reach a client before it registers and starts receiving spawns.

Connect NetworkManager.session_info_received to _on_session_info_received in _ready(), and change MAP_SCENE from a preload constant into a lookup through GameState.

4 · The selection screen

Build map_select.tscn the same way as the character select — a row of cards, one per MapData. Two differences: use the preview texture in a TextureRect rather than a 3D viewport, and only show the screen when hosting. A joining player does not choose; they are told.

So the flow becomes:

PlayerScreens, in order
HostMain menu → character select → map select → world
ClientMain menu → character select → world (map arrives from the host)

Later: travelling between maps mid-session

Once map selection works, moving a live party from a town to a dungeon is a small extension of the same machinery: the server broadcasts a "change map" RPC, every peer frees the current map and its player bodies, loads the new scene into MapRoot, and the server re-spawns everyone at the new map's spawn points. Because Main, World and PlayerSpawner never unload, the connection survives the transition untouched — which is exactly the reason the scene tree was built that way in step 1.
